# 多智能体项目管理架构设计：项目制 · 一次性 Session · 上下文纪律

> 版本：dev-1.0 ｜ 状态：设计定稿
> 关联文档：《记忆摘要服务_设计实现与API集成.md》（ame 三级摘要 + 联想词机制，本架构的记忆地基）

## 一、定位与命名纪律

本系统**不叫"平台"**。它是一组围绕"项目生命周期"协作的智能体集合：
一个长驻的项目管理者（PMO 主 agent / planner），加若干一次性的项目 agent
（设计 / 执行 / 调研 / 复盘）。叫它平台，就会往"什么都能承载"的方向膨胀，
上下文和职责都会失控——本架构的核心恰恰相反：**每个单元都有明确的生、死和边界**。

## 二、上下文纪律（一切设计的前提）

经验事实：1M 上下文窗口的模型，**100K-300K 是注意力甜区，超过 500K 开始涣散**。
涣散的本质不是遗忘，而是无关历史稀释了当前任务的相关性。

由此推出三条铁律：

1. **任何 agent 的上下文预算上限 300K**，到 250K 即触发换出流程；
2. **上下文里只放当前任务相关的东西**，其余全部是"指针"（超链接），需要时才解引用；
3. **任务结束即归档清零**，不让历史跨任务自然累积。

## 三、核心模型：项目（Project）是上下文的容器和边界

```
项目到来 → 立项（开上下文）→ 里程碑推进（渐进注入）
        → 结项（验收 + 归档到 ame）→ 关闭（清空上下文，session 销毁）
```

PMO 主 agent 的上下文在任何时刻只包含三层：

| 内容 | 大小预算 | 类比 |
|---|---|---|
| 元能力（system prompt：进度设计/拆解/验收方法论） | 固定 ~10K | 项目经理的管理素养，不随项目变 |
| 当前项目卡（目标、当前里程碑、硬约束、未完成项） | ~5-15K/项目 | 手头的项目看板 |
| 当前步骤工作集（屏幕状态、待决策项、本步材料） | 弹性 50-200K | 摊在桌上的当前文件 |

PMO 本身也守 300K 纪律：看板超限时，旧项目卡换出到 ame，只留 L1 指针。

## 四、角色谱系：session 是一次性耗材

```
PMO 主 agent（planner，唯一长驻者，上下文 = 元能力 + 项目看板）
  │  职责：立项、拆解里程碑、派单、验收、结项、转交 deliverable，
  │        以及全部档案操作（recall 资料准备、归档、还原现场、索引维护）；
  │  铁律一：【过手即弃 · 记忆】。planner 可以直接操作 ame，
  │         但记忆内容只流过不留存——recall 打包完、归档写完，
  │         立即从上下文摘除，常驻的只有 L1 卡片和指针。
  │  铁律二：【判后即弃 · 交付物】。planner 可以瞬时判读 specialist 的状态和
  │         交付物内容做验收——这是一次性判断，不需要太多上下文；
  │         判断完成立刻从上下文摘除，只留下结论（accepted/rejected + 理由摘要）。
  │         污染的不是"看过"，而是"留下"。
  │
  ├─ StaffingSpecialist（选人专家，一次性，元角色）── 产组织方案
  │     交付物 = 组织方案（流程选型 + specialist 配置 + checklist）
  │     角色配置系统内建，服务于选人阶段（见下"选人流程"）
  │
  ├─ Specialist（专家，一次性）── 解决方案设计 + 数据分析
  │     交付物 = spec（解决方案文本）或 report（分析结论报告）
  │     report 是给用户的最终答案，经 planner 转交
  │     spec 的首要意义 = 【记忆与延续性】：
  │       它是解决方案的持久载体——归档、版本化、带血缘链接，
  │       供后续 session 延续（修订、复用、归因追溯）；
  │       对 WorkBuddy 而言它只是任务书（目标+约束+验收），
  │       对组织而言它是方案资产——session 会死，spec 活着
  │     【重记忆角色】：既 recall 历史记忆，也消费 ame 中本项目的采集数据
  │     （分页取数、分批分析），因此最容易上下文超载退化。
  │     配备完整的记忆管理（见 §六）：recall、分层注入、换入换出、pin list，
  │     上下文同样硬顶 300K
  │
  ├─ WorkBuddy（执行者，一次性，可并行多个）── OpenClaw 类自主智能体
  │     本质：完整的 agentic harness（感知→决策→执行→观察的自驱循环 +
  │           工具集：adb 注入/OCR/文件操作），工作时全程自主判断；
  │           与 OpenClaw 的唯一区别 = 【无记忆】：不接 ame，只有上下文——
  │     上下文 = planner 转交的任务书（目标+约束+验收标准）+ 任务材料
  │           + 自己的短期工作记录
  │     交付物 = 工作成果（代码/数据/操作结果/调研报告）
  │     spec 因此从"步骤级说明书"减负为"目标级任务书"：
  │     执行步骤由 WorkBuddy 自主规划，常见 App 操作靠模型先验知识，
  │     spec 只需写清目标、约束、验收标准和组织特有的操作知识（SOP 要点）
  │
  ├─ Librarian（记忆管理员，按需唤醒）── L1 指针层的管理者与选书人
  │     职责：① 接收换出的 L1 卡写入 ame 索引（指针溢出管理）；
  │           ② 【选材】分析 L1 索引，根据当前需求拣选相关卡，
  │              组装成思考材料包供 specialist 使用——
  │              specialist 不自己翻索引，材料由 Librarian 配好；
  │           ③ 接受分页查找请求，按页返回 L1 卡列表；维护级联索引
  │     【自身同样守纪律】：Librarian 工作时跟着 L1 指针换入换出——
  │     每页索引用完即弃，它自己的上下文只留当前页 + 需求条件
  │
  └─ （验收/归因/复盘由 planner 以"判后即弃"方式承担，不设专职 ReviewAgent）
```

三级协作链：**Planner 定"做什么/何时算完" → Specialist 定"怎么做"（产出 spec）
→ WorkBuddy 把 spec 变成现实**。层间全部通过交付物交接，不共享上下文。

记忆访问纪律：四级梯度——**workbuddy 零记忆**（只有上下文）、
**specialist 完整记忆管理**（recall + 分层注入 + Ledger 调度）、
**planner 瞬时记忆操作 + L1 看板**（可读写 ame，过手即弃；
看板只容得下当前活跃项目的 L1 卡）、**Librarian 管指针层 + 选材**
（L1 卡超限时的写入与分页查找；按需求分析索引、组装材料包供 specialist；
自身上下文同样分页换入换出）。
同一条纪律递归应用于每一层：**任何角色的上下文都只留当前工作页，
其余全部入 ame，用指针说话。**

### 选人流程：作为元项目的组织方案

"怎么组织"本身也是一个项目，用架构自身的机制解决架构的元问题（自举）。
所有项目立项后必经【选人/选流程】标准阶段：

```
planner 立项 → 进入选人阶段 → 通知 Librarian（需求 = 任务特征）
  → Librarian 分析 L1 索引，拣选"流程方案卡 + 选人方案卡"（历史组织记忆）
  → Librarian 将材料包提交给 StaffingSpecialist（选人专家，一次性，
    其角色配置为系统内建——递归在元层终止，不再嵌套选人）
  → StaffingSpecialist 产出交付物 =【组织方案】：
      {采用哪个流程/SOP，拉哪几个 specialist，
       每个的角色 prompt 要点、任务边界、验收 checklist}
  → StaffingSpecialist 退场；Librarian 读取组织方案全文归档 + 建索引
    （组织智慧沉淀为记忆，成为下次选人的先例）
  → planner 拿到组织方案（判后即弃地读），按方案拉起对应 specialist 并派单
  → 各 specialist 上岗后按需向 Librarian 请求材料，Librarian 提供记忆
```

要点：

- **planner 零领域知识**：它只做"触发流程 + 执行方案 + 判后即弃"，
  分工判断交给懂行的 StaffingSpecialist，外行派单的风险被根治；
- **闭环自我强化**：每次组织方案归档后，下次同类任务直接命中历史方案，
  StaffingSpecialist 从"设计"退化为"确认/微调"，选人成本趋近于零；
- **Librarian 服务两个时点**：选人前供 StaffingSpecialist，上岗后供各业务
  specialist——所有角色的记忆需求都经它选材装配。

**一次性 session 原则：不并行重入、不长驻，但可还原。**

- 所有项目 agent 共享同一条生命线：诞生（立项注入）→ 工作（甜区内）
  → 交付（交付物 + 三级卡）→ 归档 → 关闭（销毁工作现场）；
- "角色"退化为一份 system prompt + 一套验收 checklist，不需要持久实体；
- **关闭 ≠ 永远死亡**。归档卡 + L3 足以把工作现场原样还原：
  需要"回头问设计者"时，启动一个新 session、从 ame 还原该项目的上下文、
  提问、再关闭。复活是一次受控的问答，不是恢复长驻；
- 设计要修改？**开新 session**，通过级联索引 recall 旧设计卡 + 取回交付物，
  产出 v2。`links` 字段记版本血缘（`supersedes: prj_xxx`）；
- 架构设计这类重思考工作**也必须**走这个模型——设计讨论最容易产生超长
  上下文，而设计完成后推演过程的价值只剩"结论 + 理由"；
- **退化即清理**：specialist 出现记忆混乱或上下文涣散迹象时，planner
  直接终止该 session，开新 specialist 重干一遍（见 §六末"退化检测与重启"）。
  一次性 session 的红利正在于此：杀一个 agent 零成本，
  因为状态都在交付物和归档卡里，不在它的脑子里。

## 五、记忆体系：三级分层 + 超链接级联索引

复用 `MemorySummaryService` 的三级结构，用途从"注入时选层级"扩展为**惰性解引用**：

```json
{
  "doc_type": "design | exec | research | review | sop",
  "project_id": "prj_20261105_007",
  "l1": "为App X实现自动签到，里程碑3/5，当前：验证码识别受阻",
  "l2": "（里程碑细节、已排除方案及原因、关键决策依据、遗留问题清单）",
  "keywords": ["AppX签到", "验证码", "控件树缺失"],
  "l3": "（原始轨迹指针：截图引用、操作序列、worker回报原文）",
  "deliverables": [
    {"path": "docs/XX架构设计.md", "type": "design-doc", "version": 2, "status": "accepted"}
  ],
  "links": ["prj_20261020_003", "memsum_ts_1698..."]
}
```

**交付物（Deliverable）是一等公民**：子 agent 的产物不只是"上下文归档"，
而是有独立生命周期的工件——设计文档、代码、报告、数据集。交付物存放在
工件区（文件库/仓库），归档卡用 `deliverables` 字段登记其路径、类型、版本、
验收状态。上下文是过程，交付物才是资产：**agent 之间真正交接的是交付物，
上下文卡只是交付物的"说明书与回忆录"**。

其中 **spec 是延续性的主载体**：session 一次性、上下文会清空，
但 spec 归档后长期存活——方案要修订，新 session 读旧 spec + 归档卡即可续写 v2；
方案要复用，Librarian 选材命中即可整体移交；出了问题要归因，
spec + 决策依据就是完整现场。**组织不 continuity 于人（session），
而 continuity 于文（spec）。**

由此推出**长程任务的接力机制（spec relay）**：

- 单 session 上下文逼近上限时，**不触发 compact**——compact 是有损压缩，
  丢弃的细节正是后期工作能力（注意力涣散之外第二大退化源）；
- 改为：把当前进展、已完成项、下一步计划**写回 spec**（spec 是活文档，
  随进度更新），交付物落库，关闭 session；
- 新 session 从 spec + 交付物状态完整重建工作现场，继续推进；
- 循环可无限进行：**任务长度从此不受上下文窗口约束**，
  只受 spec 维护质量约束——spec 里"进度状态"一节就是任务的持久状态机；
- 同一机制适用于 WorkBuddy 长任务（进度写回任务书附件）和
  Specialist 长设计（推演浓缩为决策记录追加进 spec）。

**大体量交付件数据下沉（数据泄洪）**：WorkBuddy 采集/计算产生的批量数据
（如数十条 POI 记录、整页 OCR 结果集）**禁止进入任何 agent 的上下文**——
它会炸掉窗口、造成注意力涣散。处理规则：

1. 整包写入 ame 作为**数据卡**：L1 = 一句话概览（"52 条沿途厕所 POI，
   覆盖走廊 7 段"），L3 = 原始数据本体（或工件区文件指针）；
2. 上下文（包括 planner 的看板）只出现 **L1 + 指针**；
3. 数据的主要消费者是 **Specialist**：它凭指针自行分页取数、
   分批分析（这就是"重记忆角色"的完整含义——既读历史记忆，
   也消费本项目的数据泄洪），得出结论后产出**报告交付物**转交 planner；
   WorkBuddy 只按 spec 采集/执行，不做数据分析；
4. 因此 ame 有双重角色：**跨项目的长期记忆** + **项目内的数据泄洪区**；
   数据流向固定为 WorkBuddy 采集 → ame 沉淀 → Specialist 消费 → 报告交付。

- 上下文常驻的只有 **L1 卡片**（几十字/张）——这就是"换出"；
- 需要细节时 `fetchFromAme` 展开 L2——这就是"换入"；
- `links` + `keywords`（`fetchByKeywords`）构成**级联索引**：一张卡带出一串
  相关卡，逐层深入，如同点超链接；同字段兼任版本血缘；
- L3 永不直接进 planner 上下文，仅验收争议或失败归因时取用。

## 六、上下文调度：ProjectLedger / ContextLedger

上下文记账器（Java 编排层，C++ 引擎零改动），按角色分两级配置：

**planner 侧（ProjectLedger）**——只管理看板：

- 每步估算 token；接近阈值触发驱逐；
- 驱逐顺序：最旧的非活跃里程碑 L2 → 已结项项目卡 → 最旧的观察记录；
- **钉住清单（pin list，永不驱逐）**：项目目标、当前里程碑、硬约束；
- 被驱逐内容由 planner 经 summarize 压回 ame（过手即弃），留 L1 卡片 + 指针；
- **L1 卡片本身的溢出**：看板上的 L1 卡超出容量时，批量移交 Librarian
  写入 ame 索引；需要历史项目时向 Librarian 发分页查找请求，
  按页取回 L1 卡列表（用完即弃）。**指针层也有自己的换入换出。**

**specialist 侧（ContextLedger）**——真正的记忆管理，因为 specialist
要大量处理记忆、最容易超载退化：

- 工作集 = 当前设计问题 + 已换入的记忆卡（L1 常驻，L2 按需展开）；
- recall 分批进行，每批入库前先 summarize 浓缩，禁止整批原文注入；
- 驱逐顺序：与当前设计问题相关性最低的记忆卡 L2 → 较早的推演中间稿；
- **钉住清单**：设计任务书、已确定的决策及依据、当前正在撰写的 spec 草稿；
- 推演过程稿定期压缩：中间推演是上下文膨胀的最大来源，
  每完成一个决策点，把推演过程浓缩成一行决策记录（结论+理由），原文换出。

**librarian 侧（IndexLedger）**——指针层的换入换出 + 选材：

- 上下文 = 当前需求条件 + 正在浏览的索引页（L1 卡列表），每页用完即弃；
- **选材流程**：拿到需求 → 逐页扫描 L1 索引 → 按相关性拣选 →
  组装材料包（入选卡的 L1 + 指针，必要时展开 L2）→ 交付请求方后清空；
- 材料包有体积上限（目标：注入后 specialist 仍在甜区下部），
  超限则只给最强的 N 张卡 + 其余卡的指针清单（specialist 可再请求翻页）；
- 选材质量直接影响 specialist 的启动质量：漏选关键卡 = specialist 无知开工，
  滥选 = 侵占甜区。选材命中率纳入评估指标。

**workbuddy 侧**——无 Ledger，无记忆：上下文只有 spec + 任务材料 +
短期工作记录，设计上不可能超载；若 spec 本身就超限，说明 spec 不合格，
打回 specialist 重写（spec 必须可读进甜区，这本身就是验收项）。

### 退化检测与重启（planner 的元能力之一）

**检测信号**（planner 通过回报报文和交付物间接判断，无需读 specialist 的脑子）：

- 上下文水位超限（ContextLedger 上报 token 峰值 > 300K）；
- spec 产出自相矛盾、与已归档决策冲突（说明旧记忆被错误唤回）；
- 重复索取已下发过的资料（记忆混乱的典型症状）；
- 报文格式错误率上升、长时间无里程碑进展；
- 交付物验收连续打回 ≥2 次。

**重启流程**：

1. planner 终止该 specialist session（直接清理，无协商）；
2. planner 归档现场（过手即弃），并记录**失败归因卡**（哪种混乱、发生在哪个决策点）；
3. 开新 specialist session：注入任务书 + 干净资料包 + **失败教训卡**
   （"上次在 X 处混乱，本次避开/重点复核"）；
4. 同一任务重启 ≥2 次仍失败 → 升级回 planner：说明任务粒度超出甜区容量，
   重新拆解为更小的子任务再派单。

原则：**重启不是惩罚，是上下文卫生的常规手段**——
与其带着涣散的记忆硬撑，不如清场重来，反正交付物和归档卡都在。

## 七、多智能体交互：ame 是黑板，不是消息队列

agent 之间**不共享上下文、不转贴大段记录**，交互协议只有三种报文：

```
下发：{milestone_id, 子目标(L1级), 约束, 验收标准, 资源指针[links]}
回报：{milestone_id, 状态(成功/受阻/偏差), L1级结论, 证据指针[links]}
存取：{数据卡指针, 操作(写入/分页读取/回写), 分块序号}
```

worker 的详细轨迹与批量数据写入 ame 作为 L3/数据卡；planner 上下文只落
L1 结论 + 指针。两个 agent 通过指针体系共享同一个"世界"，各自上下文保持精简。
**数据在 ame 里流转，不在上下文里流转。**

## 八、交付物交接与结项验收

下一个 agent 继续工作，靠的是"**交付物 + 归档卡**"的组合：
交付物是可继续加工的工件本体，归档卡提供它的决策依据与历史脉络。

因为"回头问设计者"需要一次受控复活（有成本），交付物仍应追求自完备：

1. **决策依据显式化**：不只"选了 A"，必须"排除 B 因为……"，
   否则后续 session 会重复踩已排除的坑；
2. **遗留问题清单**：刻意搁置的开放问题必须列全，这是给后续 session 的交接接口；
3. **结项验收（planner，判后即弃）**：planner 瞬时读入交付物，
   对照 checklist（按 `doc_type` 匹配）做内容验收，判断完成后
   立即摘除交付物内容，上下文只留验收结论 + 理由摘要。
   对应评估指标中的**交接校验失败率**；
4. **复活问答协议**：验收争议或归因时，可还原该项目上下文提问，
   问完即关闭；问答产生的新结论须追加归档（卡版本 +1），保持档案收敛。

## 九、结项仪式：关闭前的四个动作

1. **交付物登记**：工件落库，路径/类型/版本写入归档卡 `deliverables` 字段；
2. **终态摘要**：项目轨迹 → planner 执行 summarize()（过手即弃）→ 归档卡入 ame；
3. **经验萃取**：验证过的可复用流程抽成 **SOP 卡**（`doc_type=sop`）。
   下个同类项目立项时由 planner recall 命中它（过手即弃），随任务包下发，
   planner 从"重新规划"退化为"按 SOP 派单 + 偏差处理"，成本与延迟骤降；
4. **上下文清零**：项目卡移出看板，工作集丢弃，session 关闭（休眠，可还原）。

## 十一、冷启动成本与地基质量

一次性 session 的代价是冷启动注入成本。三级分层正是对冲手段：
新 session 注入的是 L1/L2 浓缩卡（几百字），不是几万字原始历史。
**因此 summarize 管线的 prompt 工程质量是整个体系的隐形地基**——
归档卡 L2 丢失关键决策依据，新 session 要么重复推演（贵），要么带缺口开工（险）。

## 十二、评估指标（验收这个架构本身）

- **任务成功率**（二值，程序化校验器判定）——主指标；
- **交接校验失败率**——结项验收被打回的比例；
- **Replan 次数 / plan 修正率**——初始分解质量的过程代理；
- **SOP 命中率**——同类任务复用 SOP 卡而非重新规划的比例（经验沉淀的量化）；
- **成本与可靠性方差**——token 开销、同任务 k 次成功率分布；
- **上下文水位**——各 agent 运行期 token 峰值是否压在 300K 内（纪律合规率）；
- **specialist 重启率**——退化清理的频率；过高说明任务拆解粒度或
  归档卡质量有问题（反馈给 planner 拆解决策与 summarize 管线）；
- **Librarian 选材命中率**——材料包中被 specialist 实际引用的卡片比例；
  漏选关键卡导致 specialist 返工索材的，记为漏选事件。

## 十三、与移动执行端的衔接

WorkBuddy 在移动端的"感官和手脚"走**标准 adb 兼容接口**（对外协议不变，
对内可替换为高速私有实现）。真机穿刺（Mi 10 / Android 13 / Magisk）实测基准：

- `screencap` 全路径 0.8-1.3s（瓶颈在 SurfaceFlinger 截图 IPC，root 无助益）；
- `uiautomator dump` ~2.4s 且可被应用掏空——视觉感知管线是主路，UI 树是辅路；
- `input tap` 净成本 ~45ms，但 adb 每条命令有 ~94ms 进程启动基线——
  执行通道需长连接复用；
- 现代设备无 fb0，快速截图无现成低层捷径，自研 HWC/合成层抓帧是必要项。

### WorkBuddy 的数据采集约束（重要）

**ame 不持有外部世界数据**（POI、实时路况、App 内信息），外部 API 也不作默认
依赖。WorkBuddy 获取世界数据的默认方式是**像人一样操作目标 App 的 GUI**：

- 感知：GPU 层截图 + OCR（结构化抽取列表/详情页字段）；
- 执行：adb 注入（tap/swipe/text）；
- spec 的写法因此改变：spec 是**目标级任务书**（目标、约束、验收标准），
  执行步骤由 WorkBuddy 自主规划（OpenClaw 类自驱循环），
  spec 只需携带组织特有的页面级知识（目标 App 的证据字段、已知坑），
  且**昂贵操作前必须设计漏斗粗筛**——GUI 操作是串行的
  （每次数秒），不能按 API 思维做大规模并行重算；
- 并行 = 多开云手机实例，每个 WorkBuddy 独占一台实例、独占一个 App 会话；
- SOP 卡沉淀的主要内容是 **GUI 操作知识**：目标 App 的页面结构、
  操作路径、证据字段模板、反风控注意事项；
- 归档卡须记数据时效：采集结果以"采集时刻 + 目标 App 为准"。

---

**一句话总纲：planner 的上下文是项目管理办公室，不是档案馆；
档案馆在 ame，靠三级分层 + 级联索引随时调卷，看完归还；
每个项目 agent 关闭前必须把智慧浓缩成卡、把成果落成交付物；
session 可休眠、可还原问答，但绝不长驻。**
